## 18-2 axios拦截器
拦截器分为 **请求拦截器** 和 **响应请求拦截器** ，作用都是在请求发送前对数据进行一定的处理

在 `axiosHelper` 中，以请求拦截器为例，讲解如何使用：

`use` 方法中一个拥有四个可选参数

```
use(
  onFulfilled?,  // 1. 成功时的回调函数（config 就在这里！）
  onRejected?,   // 2. 失败时的回调函数（error 就在这里！）
  options?       // 3. 拦截器配置项（可选参数）
): number        // 返回当前拦截器的 ID（用于 eject 销毁）
```

在请求头中加入JwtToken的拦截器

```
axios.interceptors.request.use(
    //config 代表配置，即这个拦截器要进行怎样的操作
    config => {
        // 判断 token 是否存在，如果存在，则在请求前给hearder中加上token
        if (localStorage["token"]) {
            console.log(localStorage["token"])
            config.headers.Authorization = "bearer " + localStorage["token"] // 请求头加上token
        }

        // 最后再返回出去 拦截器函数必须返回一个配置对象
        return config
    },
    error => {
        return Promise.reject(error)
    }
)
```

### 过滤器：

过滤器是一种**拦截和处理机制**，将那些与具体业务无关、但每个接口都需要做的“通用工作”（如日志记录、统一异常处理、参数校验、性能统计等）从 Controller 中抽离出来，统一在请求的特定生命周期阶段进行拦截处理。

当Http请求匹配到 `Controller` 时，他会按照顺序穿过以下**五种过滤器**：
这里的**模型绑定**指的是将请求中附带的数据(如:Json请求体 Url查询参数等)转换成 方法需要的**参数**或**对象**  
**Action**指的就是 `controller` 中的方法

```
HTTP 请求 incoming
       │
       ▼
1. Authorization Filters (授权过滤器) ─── 最早执行，判断是否有权限访问
       │
2. Resource Filters (资源过滤器)     ─── 包装整个 Action 执行过程，常用于缓存/性能监控
       │
       ├─ [模型绑定完成]
       ▼
3. Action Filters (动作过滤器)       ─── 包裹 Action 方法，常用于入参校验、修改参数
       │
       ├─ [执行控制器 Action 方法]
       ▼
4. Exception Filters (异常过滤器)    ─── 全局捕获 Action 抛出的未处理异常
       │
5. Result Filters (结果过滤器)      ─── 包裹 ActionResult 返回结果，格式化 JSON 输出
       │
       ▼
HTTP 响应 outgoing
```

| **过滤器类型**              | **对应接口**           | **典型应用场景**                                             |
| --------------------------- | ---------------------- | ------------------------------------------------------------ |
| **1. Authorization Filter** | `IAuthorizationFilter` | 非标准 API 签名校验、IP 黑白名单拦截                         |
| **2. Resource Filter**      | `IResourceFilter`      | 接口耗时统计（在最外层记录开始时间）、页面/数据缓存          |
| **3. Action Filter**        | `IActionFilter`        | **最常用！** 自动校验 `ModelState`、记录请求入参和返回值日志 |
| **4. Exception Filter**     | `IExceptionFilter`     | 全局异常捕获，把后端崩溃包装成 `{ code: 500, msg: "报错" }`  |
| **5. Result Filter**        | `IResultFilter`        | 统一接口返回值格式（如给所有返回值自动外加一层 `code, data, msg`） |

实现过滤器通常需要继承**特性基类** `Attribute` 以及代表过滤器类型的接口，如 `ActionFilterAttribute`  
过滤器通常可以标注在 `Controller` 或 `Action` 上来使用

想要实现全局生效的方式可以在 `Program.cs` 里注册：

```
// Program.cs
builder.Services.AddControllers(options =>
{
    // 全局生效，无需在任何 Controller 上贴标签
    options.Filters.Add<LogExecutionTimeAttribute>(); 
});
```

### 中间件（Middleware）与 过滤器（Filter）的区别？
很多开发者容易混淆中间件和过滤器，它们的核心区别在于 **“知不知道 MVC 的路由上下文”**：

> HTTP 请求 ➔ [中间件 Pipeline (如 Cors, Authentication)] ➔ [路由匹配] ➔ [过滤器 Pipeline] ➔ [Action 执行]

- **中间件 (Middleware)**：作用于整个 HTTP 请求管道的最外层。它**不了解**具体调用了哪个 Controller 或 Action，也拿不到 Action 的入参对象，适合处理静态文件、跨域 (CORS)、身份认证等底层通用逻辑。
- **过滤器 (Filter)**：运行在 MVC 框架内部。它**完全知道**当前请求的是哪个 Controller、哪一个 Action、接收了什么参数，能精细化控制 MVC 的业务执行过程。


### 这节写的过滤器：
将从Jwt中解析出的 `CustomerNo` 添加到 `HttpContext.Item` 中，
```
    public class CtmAuthorizationFilterAttribute : Attribute, IAuthorizationFilter
    {
        public void OnAuthorization(AuthorizationFilterContext context)
        {
            var user = context.HttpContext.User;
            ClaimsIdentity claimsIdentity = (ClaimsIdentity)user.Identity;

            foreach (var claim in claimsIdentity.Claims)
            {
                if (claim.Type == "CustomerNo")
                {
                    context.HttpContext.Items.Add("CustomerNo", claim.Value);
                }
            }
        }
    }
```

### 关于从 Context 中读取解析出来的 JwtToken：
这里的 `context.HttpContext.User` 可以将它理解成用户，用户的钱包，`user.Identity` 、`user.Identities` 则是钱包里的证件，claim则是证件上的每一条字段。

### 关于 `user.Identities`(拓展): 
`user.Identities` 中存在多个ClaimsIdentity的情况，只有在解析Jwt字符串时，使用asp.net 提供的依赖注入服务：`IClaimsTransformation` 来在当此请求里，在内存中添加相应的数据，以下是代码示例和完整生命周期
```
1. 前端 Axios 发送请求：Authorization: Bearer <JWT字符串>
       │
       ▼
2. app.UseAuthentication() 中间件拦截
   └── 用密钥验证 JWT 签名合法，解密 Payload
   └── 内存中生成 1 个初始的 ClaimsIdentity（包含 JWT 里的基础字段，如 CustomerNo）
       │
       ▼
3. 触发 IClaimsTransformation 服务（核心阶段！）
   └── 拿上一步生成的 ClaimsPrincipal 作为参数调用 TransformAsync()
   └── 开发者在这里查数据库/Redis，把查到的完整权限点打成【第 2 个 ClaimsIdentity】追加进去
       │
       ▼
4. 请求进入 MVC 管道（此时 HttpContext.User 内存里已经拥有了 2 个 ClaimsIdentity）
   └── 进入 [CtmAuthorizationFilter] / [Authorize] 校验权限
   └── 进入 Controller Action 业务代码
       │
       ▼
5. 请求结束，响应返回给前端 Vue
   └── 内存中的 ClaimsPrincipal 和 2 个 ClaimsIdentity 被 GC 回收
   └── 前端 localStorage 里的 JWT Token 字符串【从头到尾没有任何改变】
```

代码示例

```
public class CustomClaimsTransformation : IClaimsTransformation
{
    private readonly IUserRepository _userRepository; // 可以正常依赖注入数据库/服务

    public CustomClaimsTransformation(IUserRepository userRepository)
    {
        _userRepository = userRepository;
    }

    public async Task<ClaimsPrincipal> TransformAsync(ClaimsPrincipal principal)
    {
        // 如果未登录或已经追加过权限，直接返回，防止重复执行
        if (principal.Identity?.IsAuthenticated != true || principal.HasClaim(c => c.Type == "PermissionsLoaded"))
        {
            return principal;
        }

        // 1. 从第一个 ClaimsIdentity 中拿到 JWT 解出来的 CustomerNo
        var customerNo = principal.FindFirstValue("CustomerNo");

        // 2. 拿着 CustomerNo 去数据库查询这个人的完整权限列表（不用写在 JWT 里，节省体积）
        var permissions = await _userRepository.GetPermissionsByCustomerNoAsync(customerNo);

        // 3. 创建第 2 个 ClaimsIdentity，专门用来存放数据库查出来的权限
        var dbIdentity = new ClaimsIdentity("DbEnrichment");
        dbIdentity.AddClaim(new Claim("PermissionsLoaded", "true")); // 防重标记

        foreach (var perm in permissions)
        {
            dbIdentity.AddClaim(new Claim("Permission", perm));
        }

        // 4. 将第 2 个 Identity 追加到内存中的 principal 里
        principal.AddIdentity(dbIdentity);

        return principal;
    }
}
```

随后在 `program` 里注册该服务

```
// 注册声明转换服务（框架会自动在 Authentication 阶段调用它）
builder.Services.AddTransient<IClaimsTransformation, CustomClaimsTransformation>();
```
